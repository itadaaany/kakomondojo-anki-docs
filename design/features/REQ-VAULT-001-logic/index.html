    REQ-VAULT-001 Obsidian 問題管理 ロジック設計書

    1. 概要

    項目 値
    機能ID REQ-VAULT-001
    機能名 Obsidian 問題管理（分野別ファイル＋表）
    要件定義書 REQ-VAULT-001
    上流機能 REQ-INGEST-001: 取り込みデータの提供
    下流機能 REQ-ANKI-001: 問題の Anki 登録

    表スキーマ（列定義・Enum値）の詳細は ../db-design.md を参照すること。本設計書は処理ロジック視点で記述し、スキーマの一次情報は db-design.md に集約する（1情報=1箇所）。

    2. 分野からファイル名への決定ロジック

    2.1 マッピング規則

    取り込んだ問題の分野文字列（形式: 大分類 » 中分類 » 小分類、根拠: detail-design-context.md D）から、保存先 Markdown ファイル名を以下の手順で決定する。

    ステップ 処理 例
    1 » を区切りとして階層を分割する ["テクノロジ系", "データベース", "トランザクション処理"]
    2 第1階層（大分類）と第2階層（中分類）を取り出す 大分類="テクノロジ系", 中分類="データベース"
    3 {大分類}-{中分類} の形式でファイル名ベースを生成する テクノロジ系-データベース
    4 ファイル名をサニタイズする（後述 2.2 参照） テクノロジ系-データベース
    5 拡張子 .md を付与する テクノロジ系-データベース.md
    6 登録先フォルダ（設定値、デフォルト: 過去問道場）配下のパスとする 過去問道場/テクノロジ系-データベース.md

    分野文字列が空または解析に失敗した場合（第1・第2階層が取得できない場合）は 未分類.md を使用する（根拠: detail-design-context.md D）。

    2.2 ファイル名のサニタイズ方針

    Obsidian Vault および各 OS で問題になりうる文字を除去・置換する。

    対象 処理
    / \ : * ? " < > \| （OSで禁止される文字） _ に置換する
    前後の空白 トリムする
    連続するスペース・区切り文字 単一の - に正規化する
    サニタイズ後の文字列が空 未分類 にフォールバックする

    3. 表の read/write ロジック

    3.1 全体フロー

    flowchart TD
    A[問題データを受け取る] --> B[分野からファイルパスを決定]
    B --> C{対象ファイルは存在するか}
    C -- 存在しない --> D[ファイルを新規作成し表ヘッダを書き込む]
    C -- 存在する --> E[ファイルを読み込む]
    D --> F[既存表の行をパースする]
    E --> F
    F --> G[正規化URLをキーに重複判定]
    G -- 重複あり --> H[Notice: 登録済み - 出典 を表示して終了]
    G -- 重複なし --> I[問題エントリ行を生成する]
    I --> J[表の末尾に行を追記する]
    J --> K[Vault API でファイルを保存する]
    K --> L[Notice: 登録完了 を表示して終了]

    3.2 表ヘッダの生成

    対象ファイルが存在しない場合、以下の2行（ヘッダ行＋区切り行）を書き込んでファイルを新規作成する。列定義の詳細は ../db-design.md を参照。

    | 出典 | タイトル | 分野 | 問題URL |
| --- | --- | --- | --- |

    3.3 既存表のパース

    • ファイル全体を読み込み、| で区切られた Markdown テーブル行を行ごとに分割する
    • 1行目をヘッダ行、2行目を区切り行として認識し、3行目以降をデータ行とする
    • 各データ行のセルを | で分割し、トリムして構造体に変換する（提案: VaultEntry 型）
    • Markdown テーブルを含まないファイルは、ファイル末尾に表ヘッダを新規追加してから行を追記する

    4. 重複判定ロジック

    4.1 URL 正規化（重複キー）

    登録時および判定時に、問題URLを以下の手順で正規化する（根拠: detail-design-context.md G）。

    ステップ 処理
    1 scheme と host を小文字化する
    2 URL からクエリパラメータ（? 以降）を除去する
    3 URL からフラグメント（# 以降）を除去する
    4 パスの末尾スラッシュを統一する（末尾の / を除去する）

    4.2 判定スコープ

    重複判定は登録先フォルダ配下の全 Markdown ファイルを横断して行う（単一の分野ファイルではなく全ファイルが対象）。根拠: REQ-VAULT-001-3・detail-design-context.md G。

    判定手順:

    1. 登録先フォルダ配下の全 .md ファイルを列挙する
    2. 各ファイルについて 3.3 のパース処理を行い、「問題URL」列の値を収集する
    3. 収集した各URL を 4.1 の正規化手順で正規化し、登録対象URLの正規化済み値と比較する
    4. 一致するURLが1件以上存在した場合、重複と判定する

    4.3 重複時の挙動

    • 既存エントリを上書きしない（先勝ち）
    • Notice で「登録済み: {簡潔出典}」と通知して処理を終了する（根拠: REQ-VAULT-001-3）

    5. 問題エントリ行のフォーマット

    5.1 Markdown 表行の生成規則

    1問につき以下の形式で1行を生成する。列の並びは db-design.md の定義に従う。

    列 生成ルール
    出典 簡潔出典文字列（例: H20秋期 問61）をそのまま使用する
    タイトル 論点名が空でない場合は論点名、空の場合は出典文字列をフォールバックとして使用する（根拠: REQ-VAULT-001-2）
    分野 3階層フル文字列（例: テクノロジ系 » データベース » トランザクション処理）
    問題URL [{簡潔出典}]({正規化URL}) の形式（クリック可能リンク）

    5.2 出典リンクの生成例

    [H20秋期 問61](https://www.fe-siken.com/kakomon/20_aki/q61.html)
    • リンクテキストは簡潔出典文字列（{元号略記}{年}{期} 問{番号} 形式）を使用する
    • リンク先URLは 4.1 で正規化した URL を使用する
    • タイトルが空の場合でも出典リンクの形式は変わらない（タイトル列への出典フォールバックとは独立した処理）

    6. UI（Obsidian Plugin API）

    6.1 コマンド

    コマンド名 説明
    過去問道場: URLから問題を取り込む URL 入力モーダルを開く（単一行または複数行入力可）

    根拠: detail-design-context.md I。

    6.2 モーダルの動作フロー

    1. コマンド実行 → URL 入力モーダルを表示する
    2. ユーザーが URL を入力して確定する
    3. 入力された URL を1行ずつ処理する（複数行の場合は改行区切りで分割）
    4. 各 URL について REQ-INGEST-001 のスクレイピング処理を呼び出す
    5. 取得した問題データを本ロジックの write フローへ渡す
    6. 全件処理後、Notice で結果を通知する（根拠: detail-design-context.md I）

    6.3 Notice 通知一覧

    タイミング メッセージ例
    登録成功 登録 {N}件（一括の集計）
    重複登録 登録済み {N}件
